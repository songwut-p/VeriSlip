## 4. พบและแก้บั๊ก: datetime_raw หายจาก parse_slip_text()

ระหว่างเช็ค `git diff` ก่อน commit พบว่า field `datetime_raw` (string ดิบของ
วันที่-เวลาก่อน parse) หายไปจาก dict ที่ `parse_slip_text()` return ออกมา
ทั้งที่โค้ดยังคำนวณค่านี้อยู่ภายในฟังก์ชัน (แค่ไม่ได้ใส่ลง dict)

**วิธีตรวจสอบ**: ใช้ `git log -S"datetime_raw" --oneline` พบว่ามีแค่ commit เดียว
(ตอนเพิ่มเข้ามาครั้งแรก) ไม่มี commit ไหนเคยลบออก + ทดสอบจริงกับ mock slip
ทั้ง 3 ไฟล์ยืนยันว่าหายเหมือนกันหมดทุกไฟล์ → สรุปว่าเป็นการเผลอลบระหว่างแก้ไฟล์
ด้วย editor ไม่ใช่การเปลี่ยนแปลงที่ตั้งใจ

**แก้ไข**: เพิ่มบรรทัด `"datetime_raw": raw_datetime,` กลับเข้าไปใน dict ผลลัพธ์
ทดสอบยืนยันแล้วว่ากลับมาถูกต้องครบทั้ง 3 ไฟล์ และ commit เรียบร้อย

**บทเรียน**: ตรวจ `git diff` ก่อน commit ทุกครั้งมีประโยชน์จริง ช่วยจับบั๊กที่ไม่ได้ตั้งใจ
ก่อนที่จะหลุดเข้า history

## 5. ติดตั้งและทดสอบ Ollama

ติดตั้ง Ollama สำเร็จ ดึงโมเดล `qwen2.5:7b` มาทดสอบ

**ทดสอบครั้งแรก**: ให้รีวิว/วิเคราะห์โค้ดของโปรเจกต์ — ผลออกมาไม่ตรงจุด วิเคราะห์
ไปคนละทางและมีคำแนะนำที่ขัดแย้งกัน สรุปว่างานรีวิวโค้ดไม่เหมาะกับโมเดลขนาดเล็ก
(7B, quantized) ที่ VRAM จำกัด

ทดลองเทียบกับ `qwen2.5-coder:7b` (fine-tune เฉพาะโค้ด) — พบว่าตัว coder ปนภาษาจีน
เข้ามาหนักกว่าตัวธรรมดา แม้จะสั่งจำกัดเฉพาะภาษาไทย/อังกฤษไว้แล้ว สรุปว่าตัวธรรมดา
(`qwen2.5:7b`) เหมาะกับ use case ของโปรเจกต์นี้มากกว่า (ไม่ใช่ตัว coder)

**ทดสอบที่ตรงกับงานจริง**: ให้ตอบคำถามจาก context สั้นๆ (แบบเดียวกับที่ RAG จะใช้งานจริง)
เช่น "จากข้อมูลนี้... ใครเป็นผู้รับเงิน และโอนไปเท่าไหร่" — ตอบถูกต้องทั้งชื่อผู้รับและ
จำนวนเงิน สรุปว่าโมเดลพร้อมสำหรับงาน RAG แล้ว

## 6. ออกแบบโครงสร้าง RAG (ตัดสินใจเบื้องต้น)

ต้องการให้ chatbot ตอบได้ทั้งคำถามเกี่ยวกับสลิปใบเดียว และคำถามสะสมหลายใบ
(เช่น "เดือนนี้โอนไปทั้งหมดเท่าไหร่")

**ข้อสังเกตสำคัญ**: คำถามเชิงคำนวณ/รวมยอด (aggregate) ไม่เหมาะกับ vector search
เพราะ vector DB ค้นด้วยความคล้ายทางความหมาย ไม่ใช่การคำนวณ ถ้าปล่อยให้ LLM
บวกเลขเองจาก context มีความเสี่ยงตอบผิดสูง

**แนวทางที่ตกลง (hybrid)**:
- โครงสร้างจริง (SQLite หรือ JSON) — เก็บ field ที่ parse แล้ว ใช้สำหรับคำถามที่ต้อง
  คำนวณ/กรองแม่นยำ (เช่น sum ยอดเงินรายเดือน) ผ่านโค้ด query ตรงๆ ไม่พึ่ง LLM คำนวณ
- Vector DB (Chroma) — เก็บประโยคสรุปภาษาธรรมชาติของแต่ละสลิป ใช้สำหรับคำถาม
  เชิงความหมาย (เช่น "มีสลิปไหนเกี่ยวกับสุดาบ้าง")
- Flow: รับคำถาม → แยกประเภท (คำนวณ/กรอง ไปทาง SQLite, ความหมาย ไปทาง vector) →
  ส่งผลลัพธ์ให้ qwen2.5:7b เรียบเรียงเป็นคำตอบภาษาธรรมชาติ

**จุดเริ่มต้นที่ตกลงกัน**: เริ่มจากสลิปใบเดียวก่อน (ยังไม่ต้องใช้ vector DB เลย
แค่ใส่ dict ผลลัพธ์จาก parse_slip_text() เป็น context ตรงๆ ให้ qwen2.5:7b ตอบ)
พอขยายเป็นหลายใบค่อยเพิ่ม SQLite + Chroma เข้ามา

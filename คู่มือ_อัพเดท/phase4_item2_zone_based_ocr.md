# Phase 4 Item 2: Zone-based OCR (ผลจริงต่างจากแผนเดิม)

## สถานะ: เสร็จ (parser-side fixes) — zone-crop ตัวจริงยังไม่ได้ทำ

## แผนเดิม vs สิ่งที่เจอจริง
แผนแรกคือแก้ **reading-order scramble** ด้วยการ crop ภาพเป็นโซนตาม layout
(hardcode zone สำหรับ K+ และ Dime!) แต่พอลงมือ debug จริงกับไฟล์สลิปที่แชร์มา
กลับพบว่าปัญหาส่วนใหญ่ **ไม่ใช่การอ่านสลับลำดับเลย** แต่เป็น:
1. สลิปบางฟอร์แมต/แอป **ไม่มี label กำกับเลย** (เช่น "จาก"/"ถึง", "เลขที่บัญชี")
   ใช้แค่ไอคอนแทน — ทำให้ label-based regex หาไม่เจอตั้งแต่ต้น ไม่เกี่ยวกับสลับลำดับ
2. มีแอปที่ไม่เคยเจอมาก่อน ("Make by KBank") ที่ layout ต่างจาก K+ ไปเลย
3. คุณภาพภาพ/OCR misread บางจุดที่ regex แก้ไม่ได้จริง ๆ (ต้องใช้ zone/preprocessing)

## สิ่งที่แก้ใน `ocr/parse_slip.py`

### 1. รองรับ mask character แบบอื่น + PromptPay ID shape
- เลขบัญชี K+ บางไฟล์ mask ด้วย `%` แทน `x` และตัวท้ายสุดอาจเป็นตัว mask ไม่ใช่ตัวเลข
  (เดิม pattern คาดว่าต้องจบด้วยเลขเสมอ) — แก้ `ACCOUNT_NUMBER_PATTERN`
- เพิ่ม `PROMPTPAY_ID_PATTERN` แยกจากเลขบัญชีธนาคาร (คนละ shape: `xxx-xxx-####`
  ไม่มี `-เลขท้าย` แบบเลขบัญชี)

### 2. Positional fallback 3 ชั้นสำหรับชื่อผู้โอน/ผู้รับ (`parse_names()`)
เดิมพึ่ง label "จาก"/"ถึง" อย่างเดียว ตอนนี้ถ้า label หาไม่เจอ จะ fallback ตามลำดับ:
1. บรรทัดก่อนหน้า marker "ธ." (ชื่อธนาคาร) — ใช้กับ K+ ที่มี "ธ."
2. บรรทัดก่อนหน้าตำแหน่งเลขบัญชี/PromptPay ID ที่เจอ — ใช้กับแอปที่ไม่มี "ธ." เลย
   (เช่น Make by KBank); ถ้าเจอเลขบัญชี 2 ตำแหน่ง → ตัวแรก=ผู้โอน ตัวที่สอง=ผู้รับ,
   ถ้าเจอแค่ 1 ตำแหน่ง → ถือเป็นผู้รับ (จากที่สังเกต เลขบัญชีผู้โอนมักถูก OCR
   อ่านเพี้ยนจนจับไม่ได้มากกว่าฝั่งผู้รับ)
3. ทุกจุดกรองบรรทัดขยะสั้น ๆ (<3 ตัวอักษร) ออกก่อนตัดสินใจ เพราะลายน้ำตกแต่ง
   (ดอกไม้, หัวใจ ฯลฯ) บางทีถูก OCR เป็นตัวอักษรขยะ 1 ตัวแทรกอยู่ตรงกลางพอดี

### 3. Positional fallback สำหรับเลขบัญชี (`parse_account_numbers()`)
ถ้าไม่มี label "เลขที่บัญชี" เลย จะ scan ทั้งข้อความหาอะไรก็ตามที่รูปร่างเหมือน
เลขบัญชีหรือ PromptPay ID แล้วเอา 2 ตัวแรกที่เจอ (เรียงตามตำแหน่งที่ปรากฏ) มาใช้

## ผลการทดสอบ (regression check 2 รอบ, เทียบ before/after ด้วย `git stash`)
- **ไม่มี regression เลยแม้แต่ไฟล์เดียว ทั้ง 2 รอบ** — ทุกไฟล์ที่เปลี่ยนคือดีขึ้นเท่านั้น
- ผลกระทบกว้างกว่าที่ตั้งใจไว้มาก: เกือบทุกไฟล์ K+ ในชุดทดสอบ 18 ไฟล์ดีขึ้น
  (ก่อนแก้ ทุกไฟล์ K+ ขาด sender/recipient name+account ครบ 4 ฟิลด์เหมือนกันหมด)
- 3 ไฟล์ผ่านสมบูรณ์ 100% ทั้ง 4 ฟิลด์: `016206012606BOR03881`, `016206013418BOR01777`,
  `016224182249BPP10118`
- `recipient_name` กู้คืนได้เกือบทุกไฟล์ที่เหลือปัญหา หลังเพิ่ม fallback ชั้นที่ 3

## Known limitations ที่เหลืออยู่ (ยอมรับไว้ ไม่ใช่บั๊ก)
- **ผู้รับเป็นบริษัท/ร้านค้า ไม่ใช่คน** (เช่น SF Cinema, Advance MPay) — ไม่มี anchor
  ที่เสถียรพอจะดึงชื่อร้านค้าได้ทั่วไป, `recipient_name`/`recipient_account` เป็น `None`
- **`sender_name` บนสลิปแอป "Make by KBank"** — เลขบัญชีผู้โอนถูก OCR อ่านเพี้ยนเป็น
  ตัวอักษรขยะ (ปัญหาคุณภาพภาพ/OCR ไม่ใช่ parser) ทำให้ positional fallback หา
  ตำแหน่งอ้างอิงไม่ได้
- **`recipient_account`** หายในบางไฟล์ ด้วยเหตุผลเดียวกับข้างบน

## ที่ยังไม่ได้ทำ (ของเดิมที่วางแผนไว้แต่แรก)
- **Zone-based crop ตัวจริง** สำหรับเคส reading-order scramble แท้ ๆ (เช่น QR-code
  K+ จาก Phase 3, Dime! column-scramble/label-value แยกบล็อก) — ไม่ได้แตะเลยรอบนี้
  เพราะไฟล์ที่ทดสอบเพิ่มไม่มีเคสนี้ปนมา ถ้ามีเวลาเหลือค่อยกลับมาดู

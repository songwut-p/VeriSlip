# สรุปผลการทดสอบ OCR — Mock Bank Slip (Thai / English / Mixed)

วันที่ทดสอบ: 10 กรกฎาคม 2569
เครื่องมือ: Tesseract OCR (CLI)
ไฟล์ทดสอบ: `mock_slip.png` (ไทยล้วน), `mock_slip_en.png` (อังกฤษล้วน), `mock_slip_mixed.png` (ผสม Thai+English)
Layout ทั้ง 3 ไฟล์เหมือนกันทุกประการ (600x950px, ตำแหน่ง element เดียวกัน) ต่างกันแค่ภาษา/ฟอนต์ เพื่อเทียบผลแบบ apples-to-apples

## ผลการทดสอบ

| ไฟล์ | คำสั่ง (`-l`) | ผลลัพธ์โดยรวม |
|---|---|---|
| mock_slip.png (ไทยล้วน) | `tha` | ข้อความไทยถูกหมด แต่ตัวอักษร `x` (Latin) ในเลขบัญชีพัง กลายเป็นสัญลักษณ์/เลขไทย เช่น `>%%-<-%1234-5` |
| mock_slip_en.png (อังกฤษล้วน) | `eng` | ถูกต้องเกือบ 100% ยกเว้น `x` ตัวเล็กถูกอ่านเป็น `X` ตัวใหญ่ |
| mock_slip_mixed.png (ผสม) | `tha+eng` | ดีที่สุดโดยรวม เลขบัญชี (X) อ่านถูกต้อง แต่วันที่แบบย่อ "10 ก.ค. 2569" เพี้ยนเป็น "10 a.m. 2569" |
| mock_slip_mixed.png (ผสม) | `tha` (อย่างเดียว) | พังหนักที่สุด ชื่อธนาคารภาษาอังกฤษ ("Kasikorn Bank") อ่านไม่ออกเป็น "ไลร1๒๐หท ธิลท6" และเลขบัญชีพังเหมือนไฟล์ไทยล้วน |

## ข้อสรุปสำคัญ

1. **เอกสารที่มีภาษาผสม หรือแม้แต่ไทยล้วนที่มีตัวอักษรละตินปน (เช่น "x" ในเลขบัญชี) ควรใช้ `-l tha+eng` เป็นค่าเริ่มต้นเสมอ** ไม่ควรใช้ `tha` เดี่ยวๆ เพราะจะอ่านตัวอักษรละตินผิดเพี้ยนเป็นสัญลักษณ์หรือเลขไทย

2. **แม้ `tha+eng` จะดีที่สุดในภาพรวม แต่ยังมีจุดเสี่ยง**: คำย่อเดือนไทยที่มีจุดคั่น (เช่น "ก.ค.", "ต.ค.") มีโอกาสถูกตีความสับสนกับคำย่อภาษาอังกฤษ (เช่น "a.m./p.m.") เพราะรูปแบบจุดคั่นคล้ายกัน — จุดนี้อาจต้องแก้ด้วย post-processing (เช่น regex แปลง/ตรวจจับเดือนไทยย่อ) มากกว่าพึ่ง OCR ล้วนๆ

3. **ตัวเลข x/X ในเลขบัญชีเป็นจุดเปราะบางที่สุด** ของทุก config ยกเว้นตอนมี `eng` ร่วมด้วย จึงเป็นสัญญาณเตือนว่า field ที่มีอักขระผสมตัวเลข-ตัวอักษร (เช่น เลขบัญชีที่ปิดบังบางส่วน) ต้องระวังเป็นพิเศษตอนออกแบบ pipeline

4. **ข้อสังเกตเรื่อง case-sensitivity**: โมเดล `eng` มักแปลง `x` ตัวเล็กเป็น `X` ตัวใหญ่เสมอ ถ้าจะ parse ข้อมูลจริงต้องทำ `.lower()` หรือใช้ regex ที่ไม่สนตัวเล็กตัวใหญ่

## ขั้นตอนถัดไป (แผนเดิม)

- นำ config `tha+eng` ไปใช้เป็นค่าเริ่มต้นสำหรับ pipeline OCR ต่อจากนี้
- เริ่มทำ structured data extraction: parse OCR output ให้เป็น field (amount, date, bank name, account number, transaction ID)
- พิจารณา post-processing เฉพาะจุด: normalize เดือนไทยย่อ, normalize case ของตัวอักษรละติน

## Contrast sweep test (2026-07-18)

ทดสอบเพิ่ม preprocessing (grayscale + contrast enhancement) เข้าไปใน `ocr_image_to_text()`
สำหรับ mock slip ทั้ง 3 ไฟล์ โดย sweep ค่า `contrast_factor` ตั้งแต่ 1.0 (ไม่เพิ่ม contrast) ถึง 1.5

### ผลสรุป

| contrast_factor | ไทย: เดือน | ไทย: ชื่อครบ | อังกฤษ: ชื่อครบ | ผสม: เดือน | ผสม: ชื่อครบ |
|---|---|---|---|---|---|
| 1.0 | ผิด (a.m.) | ครบ | ครบ | ผิด (a.m.) | ครบ |
| 1.1–1.3 | ถูก (ก.ค.) | recipient หายบ่อย | ครบ | ถูก (ก.ค.) | ไม่แน่นอน |
| 1.4–1.5 | ถูก (ก.ค.) | ครบ (ที่ 1.5) | หายทั้งคู่ | ถูก (ก.ค.) | ครบ (ที่ 1.5) |

### ข้อสรุป

1. **ไม่มีค่า contrast_factor ค่าเดียวที่ผ่านทุกเงื่อนไขพร้อมกัน**
   - contrast สูง (1.4-1.5): ช่วยให้เดือนไทยอ่านถูก (ก.ค. แทน a.m.) แต่ทำให้ label
     ภาษาอังกฤษที่เป็นคำสั้น ("From", "To") หายไปทั้งบรรทัด ส่งผลให้ sender_name/
     recipient_name ของไฟล์อังกฤษเป็น None
   - contrast ต่ำ (1.0): ไฟล์อังกฤษอ่านได้สมบูรณ์แบบ แต่เดือนไทยอ่านผิดเป็น a.m./p.m. เสมอ

2. **พฤติกรรมไม่ smooth/ไม่ monotonic** - ในไฟล์ไทย ช่วง contrast 1.1-1.4 recipient_name
   เป็น None เกือบทุกค่า ยกเว้นที่ 1.5 พอดี (และ 1.0) แปลว่า Tesseract ไวต่อค่า contrast
   แบบไม่ต่อเนื่อง การหาค่ากลางที่ดีที่สุดด้วยการ sweep แบบนี้ไม่น่าเชื่อถือพอสำหรับใช้งานจริง

3. **สาเหตุ**: นี่คือปัญหาเชิงโครงสร้าง ไม่ใช่แค่ยังไม่เจอค่าที่เหมาะ - contrast ตัวเดียว
   ในภาพเดียวมีผลตรงข้ามกันระหว่างข้อความไทย (ต้องการ contrast สูงกว่า) กับ label
   ภาษาอังกฤษแบบคำสั้น/บาง (เสียหายง่ายเมื่อ contrast สูง)

## Zone-based preprocessing (fixed-position) test (2026-07-18)

ทดสอบ `preprocess_image_zoned()` — แบ่งภาพเป็น 2 โซนตามตำแหน่ง % แนวตั้งคงที่:
โซนบน 15% แรก (สมมติว่าเป็น header/ตัวหนา) ใช้ contrast 1.0, โซนล่างที่เหลือ (85%)
ใช้ contrast 1.5

### ผล

ไม่ช่วยอะไรเลย ผลออกมาเหมือน uniform contrast ทุกกรณี (ไทย/ผสม ยังดีเหมือนเดิม,
อังกฤษยัง `sender_name`/`recipient_name` เป็น None เหมือนเดิม)

### สาเหตุ

Label ภาษาอังกฤษที่มีปัญหาจริง ("From", "To") อยู่**กลางหน้า** (โซนเนื้อหา/body)
ไม่ใช่ 15% บนสุดของภาพตามที่สมมติไว้ สมมติฐานเรื่องตำแหน่งตายตัวผิด — ปัญหาไม่ได้
ผูกกับตำแหน่งของภาพ แต่ผูกกับ**ขนาดตัวอักษรจริง**ของแต่ละคำที่กระจายอยู่ทั่วภาพ

## Dynamic bounding-box preprocessing test (2026-07-18)

ทดสอบ `preprocess_image_dynamic()` — แก้ข้อจำกัดของ zoned (fixed-position) โดย:
1. รัน `pytesseract.image_to_data()` รอบแรกบนภาพ grayscale (ยังไม่ปรับ contrast)
   เพื่อดึงตำแหน่ง + ความสูงของแต่ละคำที่ตรวจเจอจริงในภาพ
2. หาค่ามัธยฐาน (median) ของความสูงตัวอักษรทั้งภาพ เป็นเกณฑ์อ้างอิง
3. คำที่สูงกว่ามัธยฐาน × 1.3 ถือว่าเป็นตัวใหญ่/หนา (header-like) → ใช้ contrast ต่ำ (1.0)
   คำที่เหลือ (ตัวปกติ/บาง) → ใช้ contrast สูงกว่า (1.5)
4. ปรับ contrast เฉพาะในกรอบ (bounding box) ของคำนั้นๆ แล้วประกอบภาพกลับ

### ผล (ทดสอบ full field parity กับ `parse_slip_text()` ทั้ง 10 field + วัดเวลา)

| ไฟล์ | uniform (contrast=1.5) | dynamic |
|---|---|---|
| ไทย | ทุก field ถูก | ทุก field ถูก (เหมือนกัน) |
| อังกฤษ | `sender_name`/`recipient_name` = None | **แก้ได้ครบ** ('Mr. Songwut Somchai', 'Ms. Suda Jaidee') |
| ผสม | ทุก field ถูก | ทุก field ถูก (เหมือนกัน) |

เวลาที่ใช้: dynamic ช้ากว่า uniform 1.5–1.9 เท่า (ในหน่วยจริงคือช้าขึ้น ~0.25–0.31
วินาทีต่อภาพ) — ยอมรับได้ เพราะเป็นการประมวลผลภาพนิ่งทีละใบ ไม่ใช่ real-time

### สรุปสุดท้าย

**Dynamic bounding-box preprocessing คือแนวทางที่ใช้งานได้จริง** แก้ปัญหา
bold-vs-thin text ตรงจุด (ตรวจจับขนาดตัวอักษรจริงแทนการเดาตำแหน่ง) โดยไม่มี
trade-off เสียหายที่อื่นเลย — เลือกใช้แนวทางนี้ต่อไปสำหรับ `ocr_image_to_text()`

`parse_slip.py` ตอนนี้รองรับ `preprocess_mode` 3 แบบ: `"uniform"` (default ปัจจุบัน),
`"zoned"`, `"dynamic"` — **ยังไม่ได้เปลี่ยนค่า default เป็น `"dynamic"`** (แนะนำให้เปลี่ยน
ในขั้นต่อไป เนื่องจากผลดีกว่าทุกด้านและความช้าที่เพิ่มมายอมรับได้)

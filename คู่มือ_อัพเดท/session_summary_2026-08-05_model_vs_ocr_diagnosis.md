# สรุปเซสชัน 5 ส.ค. 2569 — วินิจฉัย "ขนาดโมเดลเล็ก" vs "คุณภาพ OCR"

## เป้าหมายของเซสชันนี้

ตอบคำถาม: field ที่ยังหายไปหลัง hybrid extraction (`sender_name`, `sender_account`)
เป็นเพราะ qwen2.5:7b เป็นโมเดลเล็กเกินไป หรือเป็นเพราะสาเหตุอื่น?

## เครื่องมือที่สร้างขึ้นระหว่างทาง

- **`export_ocr_texts.py`** — ดึง raw OCR text (ก่อนเข้า parser) ของไฟล์ที่เลือกไว้
  ออกมาเป็น `.txt` เก็บใน `test_texts/`
- **`compare_extraction.py`** — import ฟังก์ชัน `_build_prompt` และ `llm_extract_fields`
  จาก `llm_fallback.py` ตัวจริงมาใช้โดยตรง (ไม่ใช่ prompt ที่พิมพ์แยกซ้ำ) เพื่อเปรียบเทียบ
  ผลจาก qwen2.5:7b กับ Claude บน prompt เดียวกันเป๊ะ

## ขั้นตอนการวินิจฉัย

### รอบที่ 1 — ทดสอบ 3 ไฟล์แรก

ทดสอบไฟล์ K+ 2 ไฟล์ + FX exchange 1 ไฟล์ ที่ `sender_account` ยังหายหลัง hybrid

**ผล:** ข้อมูลอยู่ครบใน raw OCR text ทั้ง 3 ไฟล์ แต่ qwen2.5:7b คืน `null` ทั้ง 3
ส่วน Claude ดึงถูกทั้ง 3 (prompt เดียวกันเป๊ะ)

**สาเหตุที่พบ:** few-shot examples ใน prompt เดิมสอนแค่ sender_name/recipient_name/
amount ไม่มีตัวอย่างสอน pattern เลขบัญชีที่ไม่มี label "เลขที่บัญชี" นำหน้า
(เช่น `XXX-X-X1173-x` ที่ลอยอยู่หลังชื่อธนาคารเฉยๆ)

### รอบที่ 2 — เพิ่ม few-shot example ที่ 3

เพิ่มตัวอย่างสอน pattern เลขบัญชีไม่มี label ใน `llm_fallback.py`

**ผล:** ไฟล์ K+ ไฟล์ที่ 2 แก้ได้ แต่ไฟล์ที่ 1 ยังพลาด — พบว่าไฟล์ที่ 1 มีชื่อคน 2 ชุด
ที่คล้ายกัน (ผู้โอน vs ผู้รับ นามสกุลคล้ายกัน) โมเดลเลือกชื่อที่ "ดูสมบูรณ์กว่า"
(มีนามสกุลเต็ม) แทนที่จะเลือกชุดแรกที่ปรากฏ

### รอบที่ 3 — เพิ่มโน้ตเรื่องลำดับการเลือก sender

เพิ่มคำสั่งใน prompt: ถ้ามีชื่อคนหลายชุด ให้ยึดชุดที่ปรากฏ **ก่อน** เป็น sender เสมอ
ห้ามเลือกจากความสมบูรณ์ของชื่อ

**ผล:** ไฟล์ K+ ทั้ง 2 ไฟล์ที่ทดสอบ แก้ได้ครบทั้ง sender_name และ sender_account
คะแนนรวมขยับจาก 1/6 → 4/5 (ไม่นับ edge case ไฟล์ FX ที่ field ไม่มีอยู่จริงแบบตรงไปตรงมา)

### รอบที่ 4 — ขยายทดสอบครบทั้ง 14 ไฟล์

ทดสอบทุกไฟล์ที่ `sender_account` ยังหายหลัง hybrid เดิม แบ่งตามแอป

## ผลสรุปตามแอป

### K+ (Kasikorn) — 5 ไฟล์

**4/5 ไฟล์ถูกครบทั้งสอง field** หลังแก้ prompt — ยืนยันว่าปัญหาของกลุ่มนี้คือ
**prompt ไม่ครอบคลุม pattern** ไม่ใช่ข้อจำกัดของขนาดโมเดล

ไฟล์เดียวที่ยังพลาด (`016214203541530151`) มี text pattern เหมือนไฟล์ที่แก้ได้
เป๊ะทุกอย่าง แต่ยังคืน `null` — สงสัยว่าเป็นความไม่ deterministic ของ LLM เอง
(prompt ตั้ง temperature ไว้ที่ 0.1 ไม่ใช่ 0) ยังไม่ได้ทดสอบซ้ำเพื่อยืนยัน

### Make — 4 ไฟล์

sender_name ดึงถูกเกือบหมด (กติกาเลือกชื่อชุดแรกใช้ได้ผล) แต่ sender_account
ยังดึงไม่แน่นอน — raw OCR text ของแอปนี้มี noise/ขยะปนเยอะมาก (เช่น
`"8 «61 9020 0"` ที่ไม่ใช่เลขบัญชีจริงแต่โมเดลตีความผิด)

**สรุป: ปัญหาของกลุ่มนี้คือคุณภาพ OCR (พื้นหลังกราฟิก/ไอคอน/QR รบกวนการอ่าน)
ยืนยันซ้ำกับที่วินิจฉัยไว้ตั้งแต่ 4 ส.ค. ไม่เกี่ยวกับ prompt หรือขนาดโมเดล**

### Dime/STKBML — 4 ไฟล์

**⚠️ ข้อสรุปที่แก้ไขจากที่เข้าใจผิดตอนแรก:** เดิมคิดว่าเอกสารกลุ่มนี้ (ใบยืนยัน
คำสั่งซื้อหุ้น) ไม่มี field ผู้โอนอยู่จริง (document-type mismatch) แต่พอเปิดรูปต้นฉบับ
ดูจริงๆ พบว่า **มี field นี้อยู่แน่นอน** เรียกว่า "บัญชีชำระเงิน" — มีชื่อและเลขบัญชี
ของผู้ใช้เองกำกับไว้ชัดเจน

สาเหตุจริงที่ field หายคือปัญหา OCR อีกแบบ: **Tesseract ฉีกชื่อคนออกเป็นท่อน
แล้วอ่านสลับลำดับกัน** เช่น อ่านเจอ "ทักษ์อุดมกิจ" (ท่อนท้ายนามสกุล) มา**ก่อน**
"นาย ทรงวุฒิ" (ชื่อ) พร้อมมีตัวอักษรแปลกปลอม "W" แทรกเข้ามา ทำให้ regex/LLM
ต่อชื่อกลับมาไม่ได้

**สรุป: ปัญหาของกลุ่มนี้คือ OCR-stage เช่นกัน แต่เป็นคนละกลไกกับ Make**
(Make = noise ปนในข้อความ, Dime = ชื่อถูกฉีกและสลับลำดับ) ไม่เกี่ยวกับ prompt
หรือขนาดโมเดล

### TrueMoney — 1 ไฟล์ (ทดสอบในรอบนี้)

sender_account มีอยู่ใน text จริง (`บัญชีทรูมันนี่ *#*.***.4906`) แต่รูปแบบการปิดบัง
เลข (`*#*.***`) ต่างจาก pattern ที่ prompt สอนไว้ (`XXX-X-X####`) สิ้นเชิง โมเดลเลย
ไม่จับ

**สรุป: เป็นช่องว่างของ prompt จริง (ยังไม่ได้แก้) — คนละสาเหตุกับปัญหา
สลับลำดับ sender/recipient ของ TrueMoney ที่เจอตอน 4 ส.ค.**

## ข้อสรุปภาพรวม

| กลุ่มปัญหา | สาเหตุ | เกี่ยวกับขนาดโมเดลไหม |
|---|---|---|
| K+ (ก่อนแก้) | prompt ไม่ครอบคลุม pattern | **ใช่ — แก้แล้วดีขึ้นชัดเจน** |
| Make | OCR text มี noise ปนเยอะ | ไม่เกี่ยว |
| Dime/STKBML | OCR ฉีกชื่อ+สลับลำดับ | ไม่เกี่ยว |
| TrueMoney (masking) | prompt ไม่ครอบคลุม format ปิดบังเลข | เกี่ยวบางส่วน (แก้ได้ด้วย prompt) |
| TrueMoney (สลับ sender/recipient) | OCR ทำลาย spatial cue (ลูกศร) | ไม่เกี่ยว |

**คำตอบต่อคำถามตั้งต้น:** ขนาดโมเดลมีผลจริง แต่เป็นแค่ 1 ใน 3-4 สาเหตุที่ทำให้
field หาย ต้องแยกวินิจฉัยเป็นเคสๆ ไปเสมอ ก่อนจะสรุปว่า "โมเดลเล็กเกินไป"

## `llm_fallback.py` ที่แก้ไปแล้ว (2 จุด)

1. เพิ่ม few-shot example ที่ 3 สอน pattern เลขบัญชีไม่มี label
2. เพิ่มโน้ต: เลือกชุดชื่อ/บัญชีที่ปรากฏ**ก่อน**เป็น sender เสมอ ไม่เลือกจาก
   ความสมบูรณ์ของชื่อ

(มี backup ไฟล์เดิมเก็บไว้ที่ `llm_fallback_backup_before_fewshot3.py`)

## Known limitations ที่ยังไม่แก้ (ตัดสินใจพักไว้ก่อน ไปทำ RAG component ต่อ)

- Make: ต้องแก้ที่ OCR preprocessing หรือ image quality ไม่ใช่แก้ที่ prompt
- Dime/STKBML: ต้องแก้ปัญหา Tesseract อ่านสลับลำดับคำ/บรรทัด (อาจต้องดู bounding
  box แล้วจัดเรียงใหม่เอง แทนที่จะเชื่อลำดับที่ Tesseract คืนมาตรงๆ)
- TrueMoney: ยังไม่ได้เพิ่ม prompt example สำหรับ masking format แบบ `*#*.***`
- K+ ไฟล์เดียวที่เหลือ (`016214203541530151`): ยังไม่ได้ยืนยันว่าเป็น non-determinism
  จริงหรือเปล่า

## แผนต่อไป

พักเรื่องนี้ไว้ก่อน ไปเริ่ม RAG component (single-slip Q&A) ตามแผนเดิมที่วางไว้
ตั้งแต่ 18 ก.ค. — ประเด็นข้างต้นทั้งหมดถือเป็น known limitation กลับมาแก้ทีหลัง
ถ้ามีเวลาเหลือ
